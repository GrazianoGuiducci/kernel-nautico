## 1. What this execution is proving

The first Three.js demonstrator may prove that a receiver can inspect a coherent
visual relation in which:

~~~text
one recognizable yacht
+ FORM -> BUILD -> LIVE -> RETURN
+ one meaningful continuity trace
-> product becomes more complex / changes context
-> causal identity remains legible
-> experience can visibly return toward later capability
~~~

This is primarily a perceptual/cognitive continuity proof.

It is not, by itself:

- an engineering digital-thread proof;
- a CAD/PLM continuity proof;
- a production-ready digital twin;
- an operational Spatial UI;
- a company integration;
- evidence of Ferretti/Pershing adoption;
- external human-comprehension evidence.

The execution return must preserve these distinctions.

## 2. Temporary yacht carrier gate

Do not select a runtime GLB solely because its license is permissive.

Before adopting a temporary carrier, check:

~~~text
G1 commercial-use compatible
G2 premium / credible nautical silhouette
G3 mesh/material quality sufficient for close first-encounter inspection
G4 segmentation or geometry sufficient to support BUILD without invented systems
G5 reproducible source/download and attribution
G6 reasonable browser weight or feasible optimization path
~~~

Preferred dispositions:

~~~text
PASS
  use as temporary carrier

PASS_WITH_LIMIT
  use, record exactly what BUILD/section/explode operations are not supported

REJECT
  move to next candidate
~~~

Inspect only a small set of serious candidates. Do not turn asset search into
the project.

No CC BY-NC / non-commercial-only carrier is acceptable for this company/funding
encounter path.

## 3. Asset identity rule

The temporary GLB is a carrier.

~~~text
temporary external yacht
!= Kernel Nautico visual identity
!= Ferretti/Pershing product
!= final proprietary asset
~~~

Keep model loading isolated and replacement cheap.

Record exact provenance before the asset becomes a dependency.

## 4. Four-state evidence

Produce at minimum four matched evidence captures from the same runnable
demonstrator:

~~~text
FORM.png
BUILD.png
LIVE.png
RETURN.png
~~~

If the host can capture motion reliably, also produce a short autoplay
recording/GIF/video or a frame-sequence receipt. Motion evidence is optional if
the runtime cannot capture it; do not fake it.

All four states must use the same loaded yacht identity.

## 5. Silent visual test

Before final copy is used, inspect the demonstrator with most explanatory text
suppressed.

Ask:

- Is the yacht recognizably the same object?
- Does FORM feel like origin/formation rather than a finished yacht with lines?
- Does BUILD add real engineering/material depth without inventing systems?
- Does LIVE clearly change the operating field without resetting identity?
- Does RETURN visibly have an origin and a destination?
- Does the continuity trace remain meaningful?
- Can the viewer distinguish transformation from decoration?

The silent test does not require the entire concept to be self-explanatory.

Its purpose is to prevent weak visual causality from being repaired by
paragraphs.

Afterward, restore the smallest editable orientation layer needed for a
zero-context receiver.

## 7. Same-object validation

Programmatically or structurally verify that the same runtime yacht object/root
survives all four states.

Record:

~~~text
root object / semantic id
model source hash or stable file identity where available
state transitions applied to that root
submeshes actually present
submeshes actually manipulated
materials/wireframe/clipping applied
camera presets
continuity-trace object identity
~~~

If BUILD cannot use real submesh separation because the GLB is monolithic,
record that limitation and use honest clipping/material/wireframe techniques.

Do not fabricate invisible machinery merely to create an exploded view.

## 9. Runtime / browser validation

Where actual tools permit, verify:

- clean install;
- production build;
- no console errors;
- deterministic asset load;
- graceful asset-load failure;
- responsive desktop viewport;
- reduced-motion/static path;
- state controls;
- autoplay/replay;
- inspect mode boundary;
- continuity trace across acts;
- RETURN destination;
- attribution visibility where required;
- no non-commercial media;
- no unintended network dependencies;
- screenshots from the actual runtime.

Report browser/runtime actually exercised.

Do not infer cross-browser support from one browser.

## 10. Performance observations

Do not impose an arbitrary optimization target before the artifact exists.

Record at least when measurable:

- GLB size;
- total first-load asset weight;
- obvious long tasks / stalls;
- approximate frame-rate behavior on the exercised machine;
- expensive water/postprocessing/shadow features;
- mobile/tablet risk;
- obvious optimization candidates.

Optimize only where it materially changes first-encounter quality or
shareability.

Do not turn a Three.js API trick into a competence by naming it.

## 12. Owner-native evolution proof

If a reusable difference actually changes an owner-native method during this
execution:

- record the source event that exposed it;
- identify the owner that must behave differently later;
- change the smallest competent owner on a dedicated branch;
- read back the changed method;
- record the branch/commit;
- distinguish source mutation from later behavioral assimilation;
- return no_change when existing knowledge was already sufficient.

## 13. Stop condition

Stop when the first coherent runnable demonstrator and its evidence can answer:

> Does a single yacht, one continuity relation and FORM -> BUILD -> LIVE ->
> RETURN make Kernel Nautico perceptible enough for serious inspection without
> requiring the operational UI or an industrial CAD/3D pipeline?

Do not continue into those later systems by momentum.
