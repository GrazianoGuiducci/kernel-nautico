## Why this exists

The visual representation is functioning as an epistemic probe.

By trying to make the future nautical kernel visible across one yacht lifecycle,
the workstation has exposed relations that may materially help the kernel
formation. They are returned here as **candidates**, not architecture decisions.

## F-01 — Lifecycle is better represented as a loop than a terminal chain

Initial simplified presentation:

~~~text
project -> construction -> post-sale
~~~

Visual traversal exposed a wider relation:

~~~text
FORM -> BUILD -> LIVE -> RETURN -> later FORM
~~~

"Post-sale" remains inside LIVE but cannot carry operation, service, maintenance,
upgrade, crew/owner use and learning-return by itself.

Kernel question:
does lifecycle/reentry need to be a first-class relation rather than a final
service phase?

## F-02 — The product and the Kernel transform simultaneously

The yacht changes ontology in the work:

~~~text
intention -> representation -> material product -> situated operating product
~~~

The Kernel relation can also change:

~~~text
assistant around work
-> participant in project
-> process capability
-> product/vessel capability where real
-> lifecycle relation
~~~

Kernel question:
which boundaries and owner transitions must remain explicit when the same
competence relation crosses project, organization and product instance?

## F-03 — A selected subsystem relation is a candidate first complete vertical

The visual needs one relation that survives the whole journey.

Candidate R-01:

~~~text
design reason / requirement
-> engineering definition
-> configured subsystem
-> physical assembly
-> commissioning state
-> vessel-specific identity
-> operational/service event
-> service action / consequence
-> returned learning
~~~

This may be useful beyond visualization.

It could become a candidate **minimum complete vertical** for the first Product
Development Kernel exercise because it forces the kernel to demonstrate:

- source/reason continuity;
- context recovery;
- owner/competence selection;
- configuration lineage;
- project-to-product boundary;
- product-instance reentry;
- service consequence;
- learning return.

Do not select the actual subsystem until qualified domain/company sources exist.

## F-04 — AI becomes most legible through relation continuity, not presence

A visual "AI layer" added to the yacht produces a weaker and potentially false
model.

The stronger representation is:

~~~text
meaningful relation remains reachable
while object, process state and receiving context change
~~~

This suggests a kernel-level question:
is durable capability better described by the relations it preserves/reforms
than by the visibility of an assistant interface?

## F-05 — The vessel kernel may need its own situated identity without becoming isolated

To animate LIVE coherently, the vessel needs a specific field:

- actual configuration;
- component/system identity;
- technical sources;
- service/event history;
- roles/permissions;
- pertinent specialist competences.

But RETURN requires selective relation back toward organization/service/later
products.

Kernel question:
what is the minimum product-instance boundary that preserves vessel-local
identity, privacy/authority and reentry while allowing explicitly governed
learning return?

## F-06 — Commissioning is a semantic boundary

Visual transition from BUILD to LIVE becomes much clearer when commissioning /
validation is treated as the point where:

~~~text
project-configured object
-> accepted product instance
-> lifecycle state
~~~

This may be merely a useful representation or may expose a real kernel boundary.
The formation traversal should decide.

## F-07 — Visual modularity mirrors kernel modularity only as a hypothesis

A scene can be reused across marketing, partner and investor cuts while changing
depth and emphasis.

This does **not** prove that the kernel should be packaged in the same modules.

It does suggest that one source-bound relation can support several
receiver-relative projections without duplicating the truth owner.

## Requested return from kernel formation

When the first generate-complete-kernel traversal advances, return only material
differences that change the visual narrative:

- revised lifecycle boundaries;
- revised project/product owner relation;
- first real minimum vertical;
- domain-specific process facts;
- product-instance/vessel-kernel boundary;
- learning-return constraints;
- capabilities that are current vs future.

The workstation will then revise scenes rather than preserving its current story
by inertia.
