# Nautical Design Proposal Continuity 0.1

Owner: Kernel Nautico. Formed: 2026-10-04.
Source amendment: 2026-10-04 — participatory design and progressive specification.
Scope: source-bound design contributions, progressive definition with people, and local proposals.
Implementation: the local demo and its executable contract tests.

## Function

Keep a person's original contribution meaningful while it passes through a
semantic focus, an actual coder, a visual variant and a later project decision.
This is a local incarnation of existing Product Architect, Semantic–Causal
Incarnation, Interaction Quality and causal-continuity knowledge. It does not
create a new engineering authority or duplicate those external competences.

## Design can form what the initial source does not contain

An incomplete sketch, image or idea can be the start of design. Do not treat
all absent details as failed extraction or a reason to postpone the project.
People, experience, domain competences, available sources and successive
proposals can define requirements and part specifications while work continues.
Their composition can in turn change the product-level design.

Keep the causal distinction where it matters: a fact recovered about an existing
object, a working assumption, a newly proposed specification and a person's
decision are not the same event. A proposed dimension need not have existed in
the original sketch; it must not be presented as a measured property of it.
Preserve why a definition was introduced and what it changes for related parts.
Do not demand that every detail be determined before useful design begins.

The original contribution remains available beside the developing understanding.
When an unresolved relation actually depends on a person, make that point usable
for their contribution rather than returning an abstract list of unknowns.
When a source, tool or existing competence can resolve it, let that resource
participate. Reusable learning returns to the method or owner-interface relation
that must make later design different; a single project's specification remains
project knowledge unless a transferable relation emerges.

This is a method amendment, not an implementation of requirements authoring,
image generation, CAD or manufacturing. Its public purpose and current limits
are described in `docs/PUBLIC_PURPOSE.md`.

## Operating relation in the currently exercised local workflow

1. Select an existing semantic address. Resolve the situated context through
   the shared focus controller; input modality must not create another context.
2. Verify the represented source and recorded view. Preserve the original note,
   normalized strokes, observation-frame dimensions, source identity and source
   revision before producing any interpretation.
3. Export a request carrying that immutable contribution and the exact minimum
   owner-source snapshot. A prepared file is not a sent request or an inference.
4. Give the actual receiver that request without restating its target. Record
   what sources it really read and separate those observations from its claims,
   assumptions, proposal and unresolved questions.
5. Admit a returned variant only against the original request, contribution,
   semantic context and currently applicable source binding. A safe same-view
   overlay is a proposal; it does not alter the original asset or infer a 2D to
   3D mapping.
6. Compare original and candidate on the same observation frame. A proposed
   focus target may navigate the existing semantic registry only after an
   explicit action. It supplies no decision or external effect authority.
7. Require an explicit disposition and reason. Accept selects a candidate in
   the local project; reject, defer and rework retain their distinct meanings.
   Every original, variant, decision and local receipt remains distinguishable.
8. On reentry, validate records and lineage before use, then resolve the source
   and focus again. Saved project state is not a restored focus session and does
   not authenticate its author or authorize an engineering change.

These mechanics describe the exercised file-mediated incarnation. They do not
prescribe every future design activity or make this transport the permanent
form of the competence.

## Source applicability and time

A build can bind a known source set without continuously observing its remote
owner. Record the source-set commit and content digests separately from the
runtime commit. A receipt-only runtime change does not change unchanged source
content; a materially changed source set does.

Matching bytes after a known invalidation cannot restore temporal applicability.
Retain the observed invalidation with the affected request or proposal. A new
source-qualified contribution/request is needed to continue. Merely visiting a
different focus is a reversible navigation event, not evidence that its source
has changed. Do not confuse these two relations.

This document and COMPETENCE_FIELD.md belong to the earlier build's seven bound
sources. Their amendment changes that source set even with unchanged app code.
Keep the earlier run and exported project bound to their original identities.
A future build resolves the new sources; it must not relabel the old proposal
as current or inherit the old checks as proof of the new build.

## Persistence and interrupted operation

Browser storage is a convenience cache. Explicit export/import carries the
validated project record beyond that browser; only an actual source mutation
with a receipt changes the repository. Unknown schemas and malformed imports
remain recoverable without replacing recognized state. A failed load or save
must be visible and must not silently write an empty project.

For an original identity already known locally, an imported archive must retain
the ordered prefix of observed requests, variants, decisions and invalidations.
Set equality is insufficient: reordering accept then reject could otherwise
reactivate rejected work. A fresh receiver can validate only the history it has;
this local continuity check is not distributed authentication.

The bounded implementation preserves local record relationships. It does not
prove authentication, synchronized multi-user state, remote freshness,
authoritative product configuration, CAD/PLM integration or company approval.

## Proof discipline

Observe each join separately: UI capture, request file, actual receiver/source
reads, returned variant, browser import/comparison, explicit disposition and
fresh-context reentry. A replay demonstrates the receiving behavior; it does
not claim that the coder performed another inference during the replay.

Test-controller dispositions must be attributed as such. Visual evidence must
be inspected at desktop and narrow/short viewports; assertions alone do not
establish readable comparison. A changed runtime requires its own evidence.
