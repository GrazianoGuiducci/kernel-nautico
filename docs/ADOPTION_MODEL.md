# Kernel Nautico — Adoption Model

## Principle

Adoption is not repository installation.

~~~text
public source
!= enterprise incarnation
!= integration
!= competence assimilation
!= lifecycle continuity
~~~

The public source provides a common domain base.

Real adoption begins when Kernel Nautico enters a specific operating field.

These forms describe possible relations, not mandatory stages or a fixed
installation order. The actual field can begin from a project, vessel, source,
person or opportunity and form the needed combination through useful work.

## Layer 1 — Public Domain Kernel

Owner:
GrazianoGuiducci/kernel-nautico

## Layer 2 — Field Session

A first company encounter should not begin from a preselected AI problem.

~~~text
company / product field
+ Kernel Nautico
-> what new capability could this field develop?
~~~

A useful Field Session can produce:

- a field map;
- one selected continuity relation;
- one possible complete exercise;
- required source/owner boundaries;
- a next movement only where concrete value appears.

## Layer 3 — Enterprise Incarnation

~~~text
Kernel Nautico
+ actual company environment
+ actual sources / tools / people / products
+ company-local state
+ company-local competences
-> enterprise nautical kernel
~~~

The incarnation should learn the company rather than encode invented company
assumptions in the domain base.

## Layer 4 — Integration / Co-development

When a material relation appears, the kernel can participate in actual work:

- engineering;
- programme / configuration;
- production;
- quality / commissioning;
- service / refit;
- customer / owner continuity;
- other company-native fields.

The integration surface follows the real environment.

## Layer 5 — Kernel Stewardship

Long-term value may require continuing evolution.

A stewardship relation can include:

~~~text
source refresh
+ competence evolution
+ integration continuity
+ reentry / recovery
+ new capability formation
+ consequence readback
~~~

This is not generic software maintenance.

It is maintenance of a situated operating capability.

## Layer 6 — Vessel / Product Instance

Where technically, organizationally and legally appropriate:

~~~text
enterprise incarnation
+ one yacht's legitimate configuration / lifecycle field
-> vessel-specific kernel relation
~~~

Possible responsibilities may include product identity, technical sources,
maintenance/event history, service relation and local/private knowledge.

The actual vessel boundary remains distinct from the company kernel.

## Commercial forms

The architecture can support, when formed from real use:

- paid field formation;
- setup / enterprise incarnation;
- integration project;
- co-development;
- recurring stewardship;
- product/vessel instance;
- specialized competence/integration packs;
- later licensing or partner programme.

Pricing and terms can be explored provisionally and refined through the scope
and consequences of the actual adoption relation.

## Public repository and licensing

The repository is currently public.

No permissive open-source license has been selected.

Future use rights may later take forms such as:

- source-available evaluation;
- dual licensing;
- enterprise commercial license;
- managed service / stewardship;
- certified official competence or integration packs.

Those are future Business/legal decisions, not properties inferred from public
visibility.

## What creates defensibility

~~~text
canonical source
+ evolution velocity
+ situated competence
+ integration depth
+ causal history
+ lifecycle reach
+ official stewardship
+ sibling-kernel ecosystem
-> durable advantage
~~~

The strategy is to make the official evolving source and its operating ecosystem
more valuable than a static copy.
