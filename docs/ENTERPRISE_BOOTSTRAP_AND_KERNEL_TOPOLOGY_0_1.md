## Decision

Kernel Nautico remains a **native nautical-domain kernel**.

MAIOS Project Kernel is used as a **portable project/enterprise bootstrap and
continuity substrate** where its generic functions accelerate a real adoption.

~~~text
Kernel Nautico
!= MPK with nautical vocabulary
!= a satellite subordinate to MPK

MPK
!= semantic owner of nautical truth
!= permanent required runtime for every mature KN incarnation
~~~

The useful relation is:

~~~text
Kernel Nautico domain capability
+ MPK generic project-operating capabilities where material
+ company-owned sources / systems / roles / authority
-> situated Enterprise Nautical Kernel
~~~

## Wider system topology

The current D-ND/MAIOS ecosystem is better represented as a **federated
semantic field of owner-native kernels** than as one central kernel with
subordinate satellites.


One kernel becomes pertinent because its knowledge or function changes the
movement. It does not become a subordinate service merely because another
kernel selected the current focus.

## Why MPK still matters

MPK already carries generic project-operating functions that Kernel Nautico
needs during early enterprise incarnation:

- project/context reconstruction;
- living source relations;
- system understanding;
- knowledge acquisition;
- possibility formation;
- competence formation;
- startup of an existing project;
- host adaptation / project integration;
- reentry / continuity;
- local state and knowledge persistence.

These functions are generic enough that reproducing them immediately inside KN
would create needless duplication.

Therefore:

~~~text
today:
  reuse / compose MPK functions

through real nautical use:
  observe which functions become constitutive to KN

later:
  assimilate only the nautical-native subset that real use proves necessary
  while leaving generic MPK ownership external where appropriate
~~~

This is progressive native formation, not a permanent dependency contract.

## Project / programme incarnation

Inside the enterprise incarnation, each relevant product programme or yacht
project may need its own local continuity.

Here MPK is especially useful.

~~~text
Enterprise Nautical Kernel
+ MPK project/context/state functions
+ one programme / yacht project
-> Nautical Project Instance
~~~

The project instance carries:

- current intent / owner requirements;
- source set;
- design / engineering state;
- configuration;
- programme decisions;
- procurement / production relation;
- quality / commissioning state;
- current V-01 causal chain;
- project-local learning.

Project instances remain related to, but distinct from, the enterprise kernel.

## Product-instance transition

Commissioning/acceptance remains the candidate transition:

~~~text
Nautical Project Instance
-> accepted as-built product
-> Vessel Instance
~~~

The Vessel Instance can then carry:

- actual configuration;
- installed systems/components;
- manuals / certificates;
- product identity;
- maintenance / service history;
- local/private knowledge;
- authorized crew / owner / service interaction;
- role-relative bridge/spatial UI.

Do not keep every project-development artifact hot inside the vessel.
Preserve source lineage and only the relations needed for product life.

## RETURN between levels

## MPK dependency policy

Use MPK as:

~~~text
bootstrap substrate
project continuity substrate
context/source/competence formation source
host/integration method source
project-instance carrier where useful
~~~

Do not let MPK become:

~~~text
the nautical semantic owner
a compulsory central server
the company authority owner
a permanent duplication of KN state
a reason to import generic project structure where KN already has a stronger
domain-native relation
~~~

## Native-KN promotion criterion

A generic MPK function should become locally native to Kernel Nautico only when
real nautical work shows that:

1. the function is repeatedly constitutive to nautical operation;
2. its nautical form differs materially from generic MPK behavior;
3. later KN use would otherwise depend on reconstructing the same translation;
4. the receiving KN owner can exercise and evolve it independently.

Until then, compose the external owner.

## Business / Editoriali / Design relation

Business Manager, Editoriali and Design Kernel are not runtime submodules of KN.

They are peer owner-native kernels in the wider semantic field.

~~~text
Kernel Nautico movement
-> Business becomes pertinent when value/adoption/relationship changes the move
-> Design becomes pertinent when perception/interaction changes the move
-> Editoriali becomes pertinent when language/narrative changes the move
~~~

They return compact owner-relative resultants; KN does not copy their complete
state.
